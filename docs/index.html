2. Declarative schemas

pub enum Value {
    Null,
    Bool(bool),
    Number(Number),
    String(String),
    Array(Vec<Value>),
    Object(Map<String, Value>),
}

let response: Value = serde_json::from_str("...").unwrap();

if let Value::Object(user) = response {
  if let Some(Value::String(id)) = user.get("id") {
    dbg!(id);
  }
}

response = JSON.parse("...")
puts response.dig("user", "id")

#[derive(Deserialize)]
struct Response {
  user: User
}

#[derive(Deserialize)]
struct User {
  id: String
}

let response: Response = serde_json::from_str("...").unwrap();
dbg!(response.user.id); // Always there

import z from "zod";

const ResponseSchema = z.object({
  user: z.object({
    id: z.string(),
  }),
});

const response = ResponseSchema.parse(JSON.parse("..."));
console.log(response.user.id);

Benefits

  • Documentation
  • Fail fast in one place when an assumption is broken
  • Easier to audit
  • Keep downstream code free of guards

Uses

  • Your API's responses
    • Did a database schema update change your response format?
  • Third-party API responses
    • Is an undocumented field always there?
  • Query parameters / request bodies
    • Is ?sort_by=whoops a supported value?
  • Database rows (e.g. JSON columns)
    • Did we write more data than intended?
  • As the source of truth for specs like JSON Schema

Hyrum's law

With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviours of your system will be depended on by somebody.

4. Runtime assertions

If it's not throwing exceptions then it must be correct

In Ruby APIs

  • Array#fetch (raises IndexError)
  • ActiveRecord::FinderMethods#find (raises ActiveRecord::RecordNotFound)
  • ActiveRecord::FinderMethods#sole (raises ActiveRecord::SoleRecordExceeded)

In your own code

def background_color(variant)
  case variant
  when :primary
    "red"
  when :secondary
    "grey"
  else
    raise ArgumentError "not a valid variant: #{variant}"
  end
end

Benefits

  • Fail fast if invariants are broken
  • Prevent regressions
  • Downstream code can be more confident

5. Snapshot tests

Basic principle

  1. Generate a snapshot the first time the test runs
  2. Compare subsequent runs against the snapshot, fail if they don't match
  3. Provider a mechanism to review the changes and update the snapshot if necessary

Benefits

  • Test complex outputs without writing tonnes of assertions
  • Improve your testing UX with the snapshot format
  • Catch changes to the actual output (e.g. an email template) so they can't happen accidentally

6. Results

begin
  # 100 lines of business logic
rescue StandardError => e
  flash[:error] = "Something went wrong, please try again"
  # bail out
end

Results

  1. Are in one of two possible states:
    1. A success (with an associated value)
    2. A failure (with an associated error)
  2. Require the caller to check the state before accessing the success or failure values.
type SignupResult = { ok: true; userId: string } | { ok: false; error: string };

Benefits

  • Force the caller to make a decision about how to handle critical errors (or ignore them)
  • Document error cases (don't make people guess which exceptions they need to handle)
  • Make error-handling part of regular control-flow
